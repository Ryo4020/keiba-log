## 1. 画面の目的

未認証で利用する画面群の入口。登録済みのメールアドレスとパスワードでログインし、成立後はホーム画面へ進む（`REQ-AUTH-002`）。未確認アカウントでログインを試みたときは、確認が完了していないことを示し、確認コード入力画面へ進める（#5・#7）。確認コード入力画面は、ログインを試さずに直接開くこともできる。ログアウト完了後（`REQ-AUTH-003`）、および未認証状態で認証必須画面へアクセスしたとき（`REQ-AUTH-004`）の誘導先も兼ねるが、これらの場合も本画面自体の表示は通常のログイン画面と同一であり、特別な状態は設けない。本画面からアカウント登録画面・パスワード再設定申請画面・確認コード入力画面へ進める。ソーシャルログイン・Remember me・CAPTCHAは持たない。

## 3. インタラクション仕様

### 3.1 送信・遷移

| 操作・状況 | 動作 |
|---|---|
| ログインボタン押下 | 入力値のクライアント側チェックを行う。不正がなければ送信中状態に切り替え、Cognitoの認証処理を呼ぶ。送信中は再押下できないようにする（二重送信の防止） |
| 認証成功 | ホーム画面へ遷移する（`REQ-AUTH-002` #1, #2） |
| 「パスワードをお忘れですか？」押下 | パスワード再設定申請画面へ遷移する |
| 「アカウントを作成する」押下 | アカウント登録画面へ遷移する |
| 「確認コードの入力・再送」押下 | 確認コード入力画面へ遷移する。メールアドレス入力欄の値は引き継がない（引き継ぎがないため、遷移先はメールアドレスの入力欄を出す状態になり、メールアドレス欄・確認コード欄とも空で表示される）。エラーバナーの表示中に押下した場合も同じ |
| ログアウト完了後にこの画面が表示される（`REQ-AUTH-003`） | 通常のログイン画面表示と同じ。専用の状態・案内文は設けない |
| 未認証で認証必須画面にアクセスしてこの画面へ誘導された場合（`REQ-AUTH-004`） | 通常のログイン画面表示と同じ。専用の状態・案内文は設けない |

### 3.2 入力値のチェックと不正時の表示

| 操作・状況 | 動作 |
|---|---|
| 入力値が不正（メールアドレスの形式・最大文字数、パスワードの文字数・文字種のいずれかを満たさない。値の制限は `business-rules.md` が正） | ログインを実行せず、不正な項目の入力枠をエラー表示にし、直下にその項目固有の注釈を出す（`REQ-AUTH-002` #6）。エラーバナーは出さない（項目ごとの注釈と役割が重複するため） |
| メールアドレス・パスワードのいずれか（両方の場合を含む）が未入力のまま送信 | 該当項目を入力値不正と同様に扱い、入力枠をエラー表示にする |

### 3.3 認証結果によるエラー表示

| 操作・状況 | 動作 |
|---|---|
| 認証情報不一致（メールアドレス・パスワードの組み合わせが登録内容と一致しない） | エラーバナーで「メールアドレスまたはパスワードが正しくありません」の趣旨を示す。どちらの項目が誤りかを判別できる表示はしない（`REQ-AUTH-002` #3, #4）。個々の入力枠はエラー表示にしない（どちらが誤りかを示すことになるため） |
| 未確認アカウントでのログイン試行 | 認証状態にせず（#5）、エラーバナーで「メールアドレスの確認が完了していません。確認メールに記載された確認コードを入力して、確認を完了してください。確認コードが届いていない場合や有効期限が切れた場合は、確認コードの入力画面で再送できます。」の趣旨を示し、同じバナー内に「確認コードを入力する」導線を出す（#7、UI設計上の留意点）。新規登録のやり直しは案内しない（未確認アカウントは期限切れでも削除されず、同じメールアドレスでは新規登録できないため。business-rules アカウント 項番3・5）。確認コードの自動再送はしない（再送は確認コード入力画面で行える。送信数を抑える）。個々の入力枠はエラー表示にしない |
| 未確認アカウントのエラーバナー内の「確認コードを入力する」押下 | 確認コード入力画面へ遷移し、未確認と判定されたログイン試行で送信したメールアドレスを引き継ぐ（遷移先ではメールアドレスを表示のみで示し、入力欄は出さず編集もできない。確認コード欄は空）。引き継ぎは画面遷移時のアプリ内の状態で行い、URL（クエリ文字列など）に含めない。パスワードは引き継がない |
| エラーバナー表示後に再度入力・送信する | 直前のエラーバナーは送信時にクリアし、新しい結果に応じて出し直す。バナーの表示中にメールアドレス入力欄を編集しても、次の送信まではバナーをそのまま出し、バナー内の導線が引き継ぐのは判定に使ったメールアドレスのままとする（判定に使っていないアドレスを、確認が残っているものとして渡さないため。遷移先では引き継いだメールアドレスを表示のみで示し編集できないので、判定に使っていないアドレスを渡すと遷移先で直せない） |

未確認アカウントの判定と表示の条件:

- 未確認アカウントのエラーバナーは、Cognito の認証処理が「未確認アカウントである」ことを示す応答を返したときにだけ出す。この応答は正しいパスワードを入力した未確認アカウントでのみ返る、認証情報不一致とは別の応答として扱う。
- パスワードが一致しない場合は、アカウントが未確認であっても認証情報不一致の表示にする。これにより、パスワードを知らない第三者には未確認アカウントの存在が伝わらない。
- 未確認のままパスワードを忘れた利用者はこの表示に到達できないため、導線スロットの「確認コードの入力・再送」から確認コード入力画面へ進む（business-rules アカウント 項番9 の (1)(2)。確認後に「パスワードをお忘れですか？」から再設定する）。

自動遷移ではなくバナー内の導線にした理由:

- `REQ-AUTH-002` の UI設計上の留意点は「確認が完了していないこと」と「確認コードの入力へ進む導線」を同じ場所で示すことを求めている。自動遷移では、ログインが成立しなかった理由をログイン画面上で示せず、利用者は画面が変わった理由を遷移先の文脈から推測することになる。
- エラーバナーにフォーカスを移して通知する方式（3.4）を認証情報不一致と共通にでき、スクリーンリーダー利用者にも理由が伝わったうえで、本人の操作で次へ進める。
- 確認コードは自動で再送しないため、手元に確認メールがあるか・再送が必要かを利用者が理解してから進む必要がある。バナーの案内文で再送できることを先に伝えておける。

### 3.4 共通の操作性

- 押下できる要素（ログインボタン・導線スロットの3件のリンク・エラーバナー内の導線）は最小タップ領域を下回らない。
- キーボード操作の順序は画面の視覚順に合わせる。通常時は メールアドレス → パスワード → ログインボタン → パスワードをお忘れですか？ → アカウントを作成する → 確認コードの入力・再送 → フッター。未確認アカウントのエラーバナー表示時は、先頭にエラーバナー内の「確認コードを入力する」が加わる。
- エラーバナーが表示されたとき、フォーカスをエラーバナーに移し、スクリーンリーダー利用者にも通知されるようにする。未確認アカウントのバナーでは、バナーからの次のフォーカス移動先をバナー内の「確認コードを入力する」とする。

## 4. 共通パーツ

本画面は次の2件のオーナーであり、Figmaの「共通パーツ（オーナー: ログイン画面）」フレームのコンポーネントが唯一の正となる。他画面はインスタンスとして配置し、再デザインしない。

| パーツ名 | 役割 | 他画面で流用する際の注意 |
|---|---|---|
| グローバルフッター | 全画面下部に共通表示する領域。サービス名の版権表記のみを持つ | 内容・配置は変えない。各画面のコンテンツ末尾（未認証画面ではカードの外側・下）に配置する |
| 未認証画面レイアウト | 未認証画面（ログイン／アカウント登録／確認コード入力／パスワード再設定申請／パスワード再設定）で共通する中央寄せの単一カード枠。サービス名・見出し・本文スロット・画面間の導線スロットで構成する | 見出しの文言と本文スロットの内容は画面ごとに差し替える。画面間の導線スロットは0〜3件のテキストリンクを想定し、件数は画面ごとに異なってよい（本画面は3件）。リンクは縦に並べ、件数が増えても並べ方は変えない。カードの枠・余白・サービス名の表示は変えない |

## 6. 未解決点

| # | 内容 |
|---|---|
| 1 | 未確認アカウントの判定（3.3）は、Cognito が未確認を示す応答（`UserNotConfirmedException` の想定）をパスワードが一致したときにだけ返す前提に立つ。パスワード不一致でもこの応答が返る設定・認証フローだと、パスワードを知らない第三者に未確認アカウントの存在が伝わるため、実装時に応答の条件を確認する必要がある |
| 2 | 導線スロットのテキストリンクとエラーバナー内の導線は、Figma上の見た目の高さが最小タップ領域より小さい。実装ではリンクの押下領域を最小タップ領域まで広げる前提とする（見た目の文字サイズは変えない） |
