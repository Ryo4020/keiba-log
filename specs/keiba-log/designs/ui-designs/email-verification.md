## 1. 画面の目的

未認証で利用する画面群の1つ。確認メールに記載された確認コードを入力して、対象のメールアドレスのアカウントを有効化する（`REQ-AUTH-006` #1）。確認コードが届かない・期限が切れたときは、同じ画面から確認コードを再送できる（#9）。確認と再送はメールアドレスだけで行え、パスワードの入力もログインも求めない（#10）。確認・再送の結果は、アカウントの存在・有効化状態を判別できない表示にする（#6・#11）。有効化の完了後は画面内で完了を示し、ログイン画面へ誘導する（#3）。

入口は4つ。アカウント登録の受け付け後・未確認アカウントでのログイン時は前の画面からメールアドレスを引き継ぎ、表示のみで示す（入力欄は出さず、編集もできない）。ログイン画面・パスワード再設定申請画面からの直接の経路と、再読み込み・URL を直接開いた場合はメールアドレスを引き継がないため、メールアドレスの入力欄を出す。

## 2. 表示要素

### 入力フォーム（通常時）

メールアドレスの示し方は、引き継いだとき（以下「表示のみ」）と引き継いでいないとき（以下「入力欄」）の2通り。どちらか一方だけを出す。

| 要素 | 説明 |
|---|---|
| サービス名 | 「Keiba-Log」。共通パーツ「未認証画面レイアウト」に含む |
| 見出し | 「メールアドレスの確認」。全状態で共通（完了・結果不明の状態でも変えない） |
| 案内文 | メールアドレスの確認が残っていることと、確認コードが届いていれば入力することを伝える。表示のみのときは「次のメールアドレス宛に確認コードが届いていれば、確認コードを入力してください」の趣旨、入力欄のときは「登録したメールアドレス宛に確認コードが届いていれば、メールアドレスと確認コードを入力してください」の趣旨。どちらも確認メールを送ったとは断定しない（登録済みのメールアドレスでは送られないため。`REQ-AUTH-001` UI設計上の留意点） |
| 確認するメールアドレス（表示のみ） | 表示のみのときに出す。引き継いだメールアドレスをラベル「確認するメールアドレス」とともに表示のみで示し、編集はできない（理由は 3.1）。宛先を見て、確認の対象を確かめられるようにする。見た目と扱いはパスワード再設定画面の「申請したメールアドレス」にそろえている |
| メールアドレス入力欄 | 入力欄のときに出す。確認・再送の対象のメールアドレス。値の制限は `business-rules.md` のアカウントに従う（必須・最大254文字・`ローカル部@ドメイン` 形式） |
| 結果バナー | 確認・再送の結果をフォーム単位で示す帯。種類は「エラー」（確認失敗・回数上限・通信エラー）と「案内」（再送済み）の2つ。入力欄の上に1件だけ出す（表示のみのメールアドレスはバナーより上に置き、宛先と結果を続けて読めるようにする） |
| 確認コード入力欄 | 共通パーツ「コード入力欄」（本画面がオーナー）。ラベル「確認コード」、補助テキストで確認メールに記載の数字を入力することを示す |
| 入力フィールドのエラー注釈 | 入力値が不正な項目の直下に出す、その項目固有の指摘文言（メールアドレスの注釈は入力欄のときだけ） |
| 「確認する」ボタン | 主操作。確認を実行する。送信中はラベルを「確認中…」に変えて非活性にする |
| 再送の補助テキスト | 確認コードが届かない・期限が切れた場合に新しい確認コードを受け取れることを示す |
| 「確認コードを再送する」ボタン | 副操作。確認コードの再送を実行する。送信中はラベルを「再送中…」に変えて非活性にする |
| 「ログイン画面に戻る」導線 | ログイン画面へ遷移するリンク。共通パーツ「未認証画面レイアウト」の画面間の導線スロットに1件だけ置く |
| グローバルフッター | 全画面共通。共通パーツ（オーナー: ログイン画面） |

### 確認完了

| 要素 | 説明 |
|---|---|
| 確認結果表示（完了） | 本文スロットをフォームから差し替える。完了を示すアイコン・「アカウントを有効化しました」・登録したメールアドレスとパスワードでログインするよう促す文 |
| 「ログイン画面へ進む」ボタン | 主操作。ログイン画面へ遷移する。画面間の導線スロットは使わない（次の行動を1つに絞る） |

### 確認結果不明（確認の処理で障害が起きたとき）

| 要素 | 説明 |
|---|---|
| 確認結果表示（結果不明） | 本文スロットをフォームから差し替える。情報を示すアイコン・「確認の結果を確かめられませんでした」・確認が完了している可能性があるのでログインを試すこと、ログイン時に未確認と表示されたら確認コードを再送してもう一度確認することを伝える文。完了を断定しない |
| 「ログイン画面へ進む」ボタン | 主操作。ログイン画面へ遷移する |

## 3. インタラクション仕様

### 3.1 表示時（入口ごとの初期状態）

| 操作・状況 | メールアドレス | 動作 |
|---|---|---|
| アカウント登録の受け付け後に遷移してきた（`REQ-AUTH-001` #6） | 表示のみ | 登録画面で入力したメールアドレスを表示のみで示す。確認コード欄は空。確認コードの自動再送はしない。フォーカスは確認コード欄に置く |
| 未確認アカウントでのログイン試行から遷移してきた（`REQ-AUTH-002` #7） | 表示のみ | ログイン画面で入力したメールアドレスを表示のみで示す。確認コード欄は空。確認コードの自動再送はしない（送信数を抑える）。フォーカスは確認コード欄に置く |
| ログイン画面・パスワード再設定申請画面から直接開いた | 入力欄 | メールアドレス欄・確認コード欄とも空で表示する。フォーカスはメールアドレス欄に置く |
| 再読み込み・URLを直接開いた（引き継いだメールアドレスが失われた場合を含む） | 入力欄 | 直接開いた場合と同じ（空で表示する） |

- 引き継いだメールアドレスは表示のみとし、編集させない。理由: (1) ふだんの経路（登録の直後・ログイン時）では入力欄を見せず、確認コードの入力だけに絞る。(2) 登録・ログインで送信したアドレスと異なる宛先を、その流れのまま確認の対象にしない（確認の対象は、直前に登録・ログインしたアカウントと一致させる）。
- 登録時のメールアドレスの打ち間違いは、この画面では直せない（ui-overview 画面遷移の補足で許容）。表示のみのメールアドレスを見て誤りに気づいた場合は、アカウント登録画面へ戻って正しいメールアドレスで登録し直す（受け付け後は正しいアドレスを引き継いで本画面に戻る）か、正しいメールアドレスでログイン画面・パスワード再設定申請画面からの直接の経路で入り、入力欄に入力する。
- 引き継いだメールアドレスはアプリ内の状態だけで持ち、URL（クエリ文字列など）やブラウザのストレージに残さない（閲覧履歴・アクセスログ・端末にメールアドレスを残さないため）。再読み込みなどで失われた場合は、入力欄の状態で表示する。本画面を離れたとき（ログイン画面への遷移）と、「確認完了」「確認結果不明」に切り替えたときに破棄する。
- 表示のみと入力欄は表示時に決まり、画面にいる間は切り替えない（確認・再送の結果によって入力欄に変えない）。

### 3.2 確認する

| 操作・状況 | 動作 |
|---|---|
| 「確認する」押下 | 確認コードと、入力欄のときはメールアドレスのクライアント側チェックを行う（3.4）。表示のみのときは引き継いだメールアドレスを対象にする。不正がなければ送信中に切り替え、確認を実行する。送信中は「確認する」「確認コードを再送する」の両方を非活性にする（二重送信と、確認・再送の同時実行の防止） |
| 確認に成功した（#1・#2・#3） | 本文を「確認完了」に差し替える。自動ではログイン画面へ遷移させず、「ログイン画面へ進む」で進ませる。自動ログインはしない |
| 確認できなかった（確認コードの誤り・期限切れ・対象が有効化済み・アカウントが存在しない。#4・#5・#6・#7） | すべて同じ「確認失敗」のエラーバナーを出す。文言は、入力欄のときは「メールアドレスを確認できませんでした。メールアドレスと確認コードを確かめて入力し直すか、『確認コードを再送する』で新しい確認コードを受け取ってください。」、表示のみのときは直せない項目に触れず「メールアドレスを確認できませんでした。確認コードを確かめて入力し直すか、『確認コードを再送する』で新しい確認コードを受け取ってください。」の趣旨とし、どちらも原因に触れない（文言の差は入口によるもので、アカウントの状態には依らない）。再送に進めることを同じバナーで示す（#5）。入力値は残す。個々の入力枠はエラー表示にしない（原因を示すことになるため） |
| 確認の処理で障害が起きた（architecture.md 5.2 のトリガーの失敗） | 本文を「確認結果不明」に差し替える（3.6） |
| 「確認完了」「確認結果不明」で「ログイン画面へ進む」押下 | ログイン画面へ遷移する |

### 3.3 確認コードを再送する

| 操作・状況 | 動作 |
|---|---|
| 「確認コードを再送する」押下 | 入力欄のときはメールアドレスのクライアント側チェックを行う（確認コード欄は対象外）。表示のみのときはチェックせず、引き継いだメールアドレスを対象にする。不正がなければ送信中に切り替え、再送を実行する。送信中は2つのボタンを非活性にする |
| 再送を受け付けた（未確認アカウント #9 / 有効化済み・存在しない #11） | 対象の状態にかかわらず同じ「再送済み」の案内バナーを出す。文言は「入力したメールアドレスに確認が済んでいないアカウントがある場合は、新しい確認コードを送りました。届いた確認コードを入力してください。」の趣旨（表示のみのときは「入力した」を「この」に置き換える）で、送信を断定しない。確認コード欄は空にし、フォーカスを確認コード欄に移す |

### 3.4 入力値のチェックと不正時の表示

| 操作・状況 | 動作 |
|---|---|
| メールアドレスが未入力・形式不正・最大文字数超過（入力欄のときだけ） | 確認・再送を実行せず、メールアドレスの入力枠をエラー表示にし、直下に注釈を出す。表示のみのときは引き継いだ値をそのまま使い、クライアント側チェックもエラー表示もしない（この画面では直せない値のため、指摘しても利用者が対処できない） |
| 確認コードが未入力（「確認する」押下時のみ） | 確認を実行せず、確認コードの入力枠をエラー表示にし、直下に「確認コードを入力してください」を出す |
| 確認コードの桁数・文字種 | クライアント側では判定しない（判定は確認の実行に委ね、結果は「確認失敗」と同じ表示になる）。前後の空白・途中の空白は送信前に取り除き、全角数字は半角に変換する |
| エラー表示後に再度操作する | 項目ごとのエラー表示と結果バナーは、次の確認・再送の実行時にクリアして出し直す |

入力値不正のときは結果バナーを出さない（項目ごとの注釈と役割が重複するため。ログイン画面と同じ方式）。

### 3.5 回数上限・通信エラー

| 操作・状況 | 動作 |
|---|---|
| 確認または再送の回数が上限に達した（#12） | 操作を実行できなかったことを示すエラーバナーを出す。文言は「操作の回数が上限に達したため、現在は実行できません。しばらく時間をおいてから、もう一度お試しください。」の趣旨で、確認・再送のどちらでも同じ文言にする。アカウントの有無・状態に触れない。上限・解除までの時間は表示しない（Cognito の仕様に委ねる値のため） |
| 通信エラー・想定外の失敗 | エラーバナーで「通信エラーが発生しました。通信環境を確認して、もう一度お試しください。」の趣旨を示す。入力値は残す |

### 3.6 確認結果不明（トリガーの失敗）の扱い

- 確認でトリガーが失敗した場合は、アカウントが確認済みになったかが分からない（architecture.md 5.2）。完了・失敗のどちらとも断定できないため、専用の「確認結果不明」状態にする。
- 「確認失敗」と同じ表示にしない理由: 実際には確認済みの場合、利用者が案内に従って再送・再入力をしても通らず、ログインできるのに行き詰まるため。
- 「確認完了」と同じ表示にしない理由: 未確認のままの場合に完了と断定することになるため。
- ログインを試すよう案内し、未確認のままならログイン時に本画面へ戻り、再送から確認をやり直せる。同じ確認コードでの再送信は促さない。
- 専用の状態を出しても、そこに至るには有効な確認コードを入力する必要があるため、メールアドレスの持ち主以外にアカウントの状態が伝わることはない。

### 3.7 応答と表示の対応

| 応答（architecture.md 5.2 の想定） | 表示 |
|---|---|
| 確認の成功 | 確認完了 |
| 確認: コードの誤り・期限切れ・確認済みアカウント・ユーザーが存在しない（`CodeMismatchException`・`ExpiredCodeException`・`NotAuthorizedException`・`UserNotFoundException` の想定） | 確認失敗 |
| 確認: トリガー関連のエラー | 確認結果不明 |
| 再送の成功、再送: 確認済みアカウント・ユーザーが存在しない（`InvalidParameterException`・`UserNotFoundException` の想定） | 再送済み |
| 確認・再送: 回数の超過（`LimitExceededException`・`TooManyFailedAttemptsException` の想定） | 回数上限 |
| 通信の失敗・上記以外 | 通信エラー |

画面上の文言には、例外名・サービス名・設計ドキュメント名を出さない。

### 3.8 共通の操作性

- メールアドレス入力欄（入力欄のとき）はメールアドレス用の入力種別・自動入力（`type="email"`・`autocomplete="email"`）にする。
- 表示のみのメールアドレスは、パスワード再設定画面の「申請したメールアドレス」と同じく読み取り専用のユーザー名として扱う（`autocomplete="username"`）。パスワードマネージャーなどがアカウントを結び付けられるようにするためで、編集はできず、フォーカス順にも含めない。スクリーンリーダーではラベル「確認するメールアドレス」とあわせて読み上げられるようにする。
- 確認コード入力欄は数字のキーボードが出る入力にする（`inputmode="numeric"`・`autocomplete="one-time-code"`）。先頭の0を落とさないよう数値型の入力欄（`type="number"`）にはしない。貼り付けを妨げない。入力の完了や貼り付けで自動送信はしない。
- 結果の表示に原因ごとの差を作らない。文言・バナーの種類・色・表示を続ける時間を、確認失敗の原因によって変えない。期限切れだけ注意喚起の色にすることもしない。結果バナーは自動で消さず、次の操作までそのまま出す。
- 押下できる要素（2つのボタン・導線リンク）は最小タップ領域を下回らない。
- キーボード操作の順序は画面の視覚順に合わせる。
  - 入力欄のとき: メールアドレス → 確認コード → 確認する → 確認コードを再送する → ログイン画面に戻る → フッター
  - 表示のみのとき: 確認コード → 確認する → 確認コードを再送する → ログイン画面に戻る → フッター（表示のみのメールアドレスはフォーカス順に含めない）
- 結果バナーが出たときはフォーカスをバナーに移し、スクリーンリーダーにも通知する。「確認完了」「確認結果不明」に切り替わったときは結果の見出しにフォーカスを移す。

## 4. 共通パーツ

### オーナーとして作成したパーツ

本画面は「コード入力欄」のオーナーであり、Figma の「共通パーツ（オーナー: 確認コード入力画面）」フレームのコンポーネントが唯一の正となる。

| パーツ名 | 役割 | 他画面で流用する際の注意 |
|---|---|---|
| コード入力欄 | メールに記載されたコード（確認コード・再設定コード）を入力する欄。ラベル・補助テキスト・入力枠・エラー注釈で構成する | パスワード再設定画面では、ラベル・補助テキスト・プレースホルダー・エラー注釈をテキストプロパティで再設定コード用に差し替える（Figma に使用例あり）。エラーはバリアント「状態=エラー」で表す。入力の種類・自動入力・空白除去・全角数字の変換は 3.4・3.8 と同じ扱いにする。コードの誤り・期限切れなど結果の判定はこのパーツでは表さず、流用先の画面のフォーム単位の表示で扱う |

### 利用するパーツ

| パーツ名 | オーナー画面 |
|---|---|
| 未認証画面レイアウト | ログイン画面 |
| グローバルフッター | ログイン画面 |

表示のみのメールアドレス（確認するメールアドレス）は共通パーツではない。パスワード再設定画面の「申請したメールアドレス」と見た目・扱いをそろえて本画面内に配置しており、コンポーネント化していない。
