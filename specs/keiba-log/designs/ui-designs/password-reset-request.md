## 1. 画面の目的

未認証で利用する画面群の1つ。パスワードを忘れたユーザーがメールアドレスを入力してパスワード再設定を申請し、再設定コードを記載したメールを受け取る（`REQ-AUTH-007`）。申請を受け付けると、メールアドレスの登録状態（未登録・未確認アカウント・有効化済みアカウント）や申請回数の上限到達にかかわらず、常に同じタイミングでパスワード再設定画面へ進む（#6・#7・#9）。この画面はメールアドレスの入力のみを扱い、再設定コード・新しいパスワードは扱わない。本画面からログイン画面と確認コード入力画面へ進める。

## 2. 表示要素

| 要素 | 説明 |
|---|---|
| サービス名 | 「Keiba-Log」。共通パーツ「未認証画面レイアウト」に含む |
| 見出し | 「パスワード再設定の申請」。共通パーツ「未認証画面レイアウト」の見出しスロットに入れる画面固有の文言 |
| エラーバナー | 通信エラー・想定外の失敗のときにだけフォームの先頭に出す帯。アカウントの状態に触れない文言にする。ログイン画面・確認コード入力画面・アカウント登録画面のエラーバナーと同じ見た目 |
| 案内文 | 登録済みのメールアドレスを入力すること、再設定コードを記載したメールを送ることを伝える短い説明文 |
| メールアドレス入力欄 | パスワード再設定を申請する対象のメールアドレス。値の制限は `business-rules.md` の「エンティティ項目定義 > アカウント」に従う（必須・最大254文字・`ローカル部@ドメイン` 形式）。パスワードの入力欄は持たない |
| 入力フィールドのエラー注釈 | 入力値が不正なときに入力欄の直下に表示する、その項目固有の指摘文言 |
| 申請ボタン | フォームを送信する主操作。送信中はラベルを変え非活性にする |
| 補足文（未確認アカウント） | 「メールアドレスの確認が済んでいないアカウントには再設定コードが届かないため、先に『確認コードの入力・再送』から確認を完了する」趣旨の固定の文言。入力値や申請の結果によらず常に同じ内容を出す（business-rules アカウント 項番4・9） |
| 「ログイン画面に戻る」導線 | ログイン画面へ遷移するリンク |
| 「確認コードの入力・再送」導線 | 確認コード入力画面を直接開くリンク。文言はログイン画面の同じ導線と同一 |
| グローバルフッター | 全画面共通。共通パーツ（オーナー: ログイン画面） |

未認証画面レイアウト（共通パーツ）の「本文スロット」に、エラーバナー（エラー時のみ）・案内文・メールアドレス入力欄・申請ボタン・補足文をまとめたフォームを配置する。「画面間の導線スロット」には「ログイン画面に戻る」「確認コードの入力・再送」の2件を配置し、通常・送信中・各エラーのすべての状態で同じものを出す。

## 3. インタラクション仕様

### 3.1 送信・遷移

| 操作・状況 | 動作 |
|---|---|
| 申請ボタン押下 | 入力値のクライアント側チェックを行う。不正がなければ送信中状態に切り替え、パスワード再設定申請の処理を呼ぶ。送信中は再押下できないようにする（二重送信の防止） |
| 申請を受け付けた | パスワード再設定画面へそのまま遷移する（`REQ-AUTH-007` #9）。本画面では遷移前の案内表示は出さない（「登録済みのメールアドレスであれば再設定コードを記載したメールが届く」趣旨の案内は遷移先の冒頭に置かれるため、二重にしない） |
| 遷移時のメールアドレスの引き継ぎ | 申請で送信したメールアドレスをパスワード再設定画面へ引き継ぐ。引き継ぎは画面遷移時のアプリ内の状態で行い、URL（クエリ文字列など）に含めない。遷移先はこのメールアドレスと、入力された再設定コード・新しいパスワードで再設定を実行する |
| 「ログイン画面に戻る」押下 | ログイン画面へ遷移する |
| 「確認コードの入力・再送」押下 | 確認コード入力画面へ遷移する。メールアドレス入力欄の値は引き継がない（遷移先はメールアドレス欄・確認コード欄とも空で表示される）。エラーバナー・入力フィールドのエラー表示中に押下した場合も同じ |

### 3.2 受け付けとして扱う応答

次の応答はすべて「申請を受け付けた」として扱い、遷移先・表示・遷移までの時間に差を作らない（`REQ-AUTH-007` #6・#7）。

| 応答 | 扱い |
|---|---|
| 申請の成功 | 受け付け。パスワード再設定画面へ遷移する |
| 存在しないメールアドレス・未確認アカウントでの申請 | ユーザー存在エラーの抑止により成功と同じ応答になる想定（メールは送られない。#3・#4）。受け付けとして扱う |
| 申請回数の超過（`LimitExceededException` の想定） | 上限到達を判別できる表示をしてはならないため（#5・#7）、エラーとして表示せず受け付けとして扱う。成功時と同じタイミングで同じ遷移をする |

### 3.3 受け付け以外の応答

| 操作・状況 | 動作 |
|---|---|
| 通信エラー・想定外の失敗 | 画面にとどまり、入力したメールアドレスを残したまま、フォームの先頭にエラーバナーで「申請を完了できなかったこと・通信環境を確認して時間をおいて再度試すこと」の趣旨を示す。アカウントの登録状態・申請回数に触れる文言は使わない。入力枠はエラー表示にしない |
| エラーバナー表示後に再度送信する | 直前のエラーバナーは送信時にクリアし、新しい結果に応じて出し直す |

### 3.4 入力値のチェックと不正時の表示

| 操作・状況 | 動作 |
|---|---|
| 入力値が不正（メールアドレスの形式・最大文字数を満たさない） | 申請を実行せず、入力枠をエラー表示にし、直下に項目固有の注釈を出す（`REQ-AUTH-007` #8）。エラーバナーは出さない |
| メールアドレスが未入力のまま送信 | 未入力を入力値不正と同様に扱い、入力枠をエラー表示にする |
| エラー表示後に再度入力・送信する | 直前の入力フィールドのエラー表示は送信時にクリアし、新しい結果に応じて出し直す |

### 3.5 共通の操作性

- 押下できる要素（申請ボタン・導線スロットの2件のリンク）は最小タップ領域を下回らない。
- キーボード操作の順序は画面の視覚順に合わせる。メールアドレス → 申請ボタン → ログイン画面に戻る → 確認コードの入力・再送 → フッター。補足文はフォーカス対象にしない。
- エラーバナーが表示されたとき、フォーカスをエラーバナーに移し、スクリーンリーダー利用者にも通知されるようにする。
- 補足文はメールアドレス入力欄の説明として読み上げられるよう関連付ける。

## 4. 共通パーツ

本画面は共通パーツのオーナーではない。「グローバルフッター」「未認証画面レイアウト」はログイン画面の既存デザインを流用し、再デザインしていない。エラーバナーは共通パーツではなく、ログイン画面・確認コード入力画面・アカウント登録画面と同じ見た目で配置している。

| パーツ名 | オーナー画面 |
|---|---|
| グローバルフッター | ログイン画面 |
| 未認証画面レイアウト | ログイン画面 |

## 6. 未解決点

| # | 内容 |
|---|---|
| 1 | 3.2 は、ユーザー存在エラーの抑止を有効にした Cognito が、存在しないメールアドレス・未確認アカウントでの申請に成功と同じ応答を返す前提に立つ。未確認アカウント（確認済みのメールアドレスを持たないユーザー）に対して別のエラー（`InvalidParameterException` など）が返る設定・条件があると、3.3 のエラーバナーが出てアカウントの状態が判別できてしまう（#6 に反する）。実装時に応答の種類を確認し、アカウントの状態によって返り分かれる応答はすべて受け付けとして扱う必要がある |
| 2 | 申請回数の超過を受け付けとして扱うため（3.2）、上限に達した利用者は再設定画面へ進んでも再設定コードが届かない。届かないときの案内と再申請への戻り方は遷移先の担当で扱う前提とし、本画面では扱っていない |
| 3 | 申請ボタンのラベル（「再設定メールを送信する」）は今回の修正範囲外のため変えていない。メールの名称（パスワード再設定メール）とは合っているが、再設定コード方式に合わせて文言を見直すかの判断が必要 |
| 4 | 送信中フレーム（`59-2`）のメールアドレス入力欄がプレースホルダーの表示のままで、入力済みの値の表示になっていない。今回の修正範囲外のため変えていない |
| 5 | 導線スロットのテキストリンクは、Figma上の見た目の高さが最小タップ領域より小さい。実装ではリンクの押下領域を最小タップ領域まで広げる前提とする（見た目の文字サイズは変えない） |
