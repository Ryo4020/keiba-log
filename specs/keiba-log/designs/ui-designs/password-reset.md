## 1. 画面の目的

未認証で利用する画面群の1つ。パスワード再設定申請画面から進み、パスワード再設定メールに記載された再設定コードと新しいパスワードを同じ画面で入力して、新しいパスワードを設定する（`REQ-AUTH-008` #1・#3）。再設定コードが本人確認の役割を果たすため、現在のパスワードは求めない。再設定コードが使えなかったときは、入力し直しと申請のやり直しの両方に進める（#11）。設定が完了しても認証状態にはせず、ログイン画面へ誘導する（#7）。

入口はパスワード再設定申請画面からの遷移のみ。申請画面は申請の結果（成功・存在しないメールアドレス・未確認アカウント・申請回数の超過）にかかわらず同じように本画面へ遷移し、申請に使ったメールアドレスをアプリ内の状態で引き継ぐ（URL には含めない）。

## 2. 表示要素

見出しは全状態で「パスワードの再設定」とし、状態によって変えない。

## 3. インタラクション仕様

### 3.1 表示時の分岐

| 操作・状況 | 動作 |
|---|---|
| パスワード再設定申請画面から遷移してきた（メールアドレスを引き継いでいる） | 入力フォームを表示する。再設定コード欄・パスワード入力ブロックは空。フォーカスは再設定コード欄に置く |
| メールアドレスを引き継いでいない（再読み込み・URLを直接開いた・ブラウザの履歴から戻った） | 「引き継ぎなし」を表示する。入力フォームは出さず、再設定を実行できないようにする |

- 本画面ではメールアドレスを入力させない。理由: (1) 入口を申請画面からの遷移だけにする方針（ui-overview 画面遷移の補足）と揃い、URL を開くだけで使える経路を作らない。(2) メールアドレスの誤りと再設定コードの誤りはどちらも同じ「コード誤り・期限切れ」の表示になるため、ここで入力できると原因の切り分けがさらに難しくなる。申請画面でメールアドレスを確かめて申請し直すほうが確実に進める。(3) 申請画面で入力済みの値を二度入力させない。
- 引き継いだメールアドレスはアプリ内の状態だけで持ち、URL（クエリ文字列など）や画面上の入力値として送り直さない。本画面を離れたとき（ログイン画面・申請画面への遷移、更新完了）に破棄する。
- 再読み込みなどでメールアドレスが失われた場合は、タブ内でも保持せず（ブラウザのストレージなどにも残さない）、「引き継ぎなし」を表示して申請し直してもらう。申請し直すと新しい再設定コードが発行され、申請回数・試行回数の上限（`business-rules.md` Cognito の仕様に委ねる値 #7）に近づくが、これは許容する。
- 再設定コードの有効期限は送信して初めて分かるため、表示時に残り時間・期限などを前提とした表示はしない（`REQ-AUTH-008` UI設計上の留意点）。

### 3.2 再設定する

| 操作・状況 | 動作 |
|---|---|
| 「パスワードを再設定する」押下 | 再設定コード・新しいパスワード・新しいパスワード（確認）のクライアント側チェックを行う（3.4）。不正がなければ送信中に切り替え、引き継いだメールアドレス・再設定コード・新しいパスワードで再設定を実行する。送信中は2つのボタンを非活性にする（二重送信と、送信中の画面離脱の防止） |
| 「パスワード再設定を申請し直す」押下 | パスワード再設定申請画面へ遷移する。入力中の値は破棄する |
| 「ログイン画面に戻る」押下 | ログイン画面へ遷移する。入力中の値は破棄する |
| 更新完了・更新結果不明で「ログイン画面へ進む」押下 | ログイン画面へ遷移する。自動では遷移させない |
| 更新結果不明で「パスワード再設定を申請し直す」押下 | パスワード再設定申請画面へ遷移する |
| 引き継ぎなしで「パスワード再設定を申請する」押下 | パスワード再設定申請画面へ遷移する |

### 3.3 応答と表示の対応

| 応答（例外名は想定） | 表示 | 入力値・フォーカス |
|---|---|---|
| 再設定の成功（#1・#6） | 更新完了。ユーザーを認証状態にしない（#7）。再設定前のすべての端末のログイン状態は終了する（#12。反映に時間がかかる場合がある）ため、完了の文でログインし直しが必要なことに触れる | 入力値と引き継いだメールアドレスを破棄する。結果の見出しにフォーカスを移す |
| 再設定コードの誤り・期限切れ（`CodeMismatchException`・`ExpiredCodeException`。#10・#11） | コード誤り・期限切れのエラーバナー。文言は「パスワードを再設定できませんでした。再設定コードを確かめて入力し直すか、『パスワード再設定を申請し直す』から新しい再設定コードを受け取ってください。」の趣旨。誤りと期限切れを同じ表示にする（期限切れだけ区別すると、再設定コードが発行された＝アカウントが存在することが分かるため）。再設定コード欄はエラー表示にしない（メールアドレス側が原因の場合もあり、コードが原因だと示すことになるため） | 再設定コード・新しいパスワード・確認入力はすべて残す（再設定コードの打ち間違いを直すだけで送り直せるように。パスワードは条件を満たしているため打ち直させない）。バナーにフォーカスを移す |
| 新しいパスワードが条件を満たさない（`InvalidPasswordException`。クライアント側チェックをすり抜けた場合） | 新しいパスワード欄の項目エラー。注釈はパスワード入力ブロックのオーナーの定義（`signup.md` 3.3 の「パスワードがポリシーに合わないと返された」場合）に従う。エラーバナーは出さない | 入力値は残す。新しいパスワード欄にフォーカスを移す |
| 試行回数の超過（`LimitExceededException`・`TooManyFailedAttemptsException`。#13） | 回数上限のエラーバナー。文言は「操作の回数が上限に達したため、現在はパスワードを再設定できません。しばらく時間をおいてから、もう一度お試しください。」の趣旨。上限・解除までの時間は表示しない（Cognito の仕様に委ねる値のため） | 入力値は残す。バナーにフォーカスを移す |
| トリガー関連のエラー（`UserLambdaValidationException`・`UnexpectedLambdaException` などの想定。他端末のログイン状態を終了させる処理の失敗） | 更新結果不明（3.5） | 入力値と引き継いだメールアドレスを破棄する。結果の見出しにフォーカスを移す |
| 通信の失敗・上記以外 | 通信エラーのエラーバナー。文言は「通信エラーが発生しました。通信環境を確認して、もう一度お試しください。」の趣旨 | 画面にとどまり、入力値は残す。バナーにフォーカスを移す |

- 画面上の文言には、例外名・サービス名・設計ドキュメント名を出さない。
- 結果の表示に原因ごとの差を作らない。コード誤りと期限切れで、文言・バナーの種類・色・表示を続ける時間を変えない。期限切れだけ注意喚起の色にすることもしない（ui-overview `color-warning` の注記）。エラーバナーは自動で消さず、次の送信までそのまま出す。

### 3.4 入力値のチェックと不正時の表示（#9）

| 操作・状況 | 動作 |
|---|---|
| 再設定コードが未入力 | 再設定を実行せず、再設定コード欄を「状態=エラー」にし、直下に「再設定コードを入力してください」を出す |
| 再設定コードの桁数・文字種 | クライアント側では判定しない（判定は再設定の実行に委ね、結果は「コード誤り・期限切れ」と同じ表示になる）。前後・途中の空白は送信前に取り除き、全角数字は半角に変換する |
| 新しいパスワードが未入力・強度要件を満たさない・最大文字数を超える | 再設定を実行せず、新しいパスワード欄をエラー表示にし、直下に注釈を出す。値の制限・注釈の文言・強度要件の一覧の扱いは、パスワード入力ブロックのオーナーの定義（`signup.md` 3.3。強度要件を満たさない場合と最大文字数を超えた場合の注釈）に従い、本画面では独自に定めない |
| 新しいパスワード（確認）が未入力・一致しない | 再設定を実行せず、確認入力欄をエラー表示にし、直下に「新しいパスワードと一致しません」（未入力のときは入力を促す文言）を出す |
| エラー表示後に再度送信する | 項目ごとのエラー表示とエラーバナーは、次の送信時にクリアして出し直す |

- 入力値不正のときはエラーバナーを出さない（項目ごとの注釈と役割が重複するため。確認コード入力画面・ログイン画面と同じ方式）。
- 不正な項目が複数あるときは、すべての項目に注釈を出し、先頭の不正な項目にフォーカスを移す。

### 3.5 更新結果不明（トリガーの失敗）の扱い

- 再設定の処理の中で他端末のログイン状態を終了させる処理が失敗した場合、パスワードが更新されたかどうかが分からない。完了・失敗のどちらとも断定できないため、専用の「更新結果不明」状態にする（確認コード入力画面の「確認結果不明」と同じ考え方）。
- 「コード誤り・期限切れ」と同じ表示にしない理由: 実際には更新済みの場合、再設定コードは使用済みで通らず（#6）、入力し直しても行き詰まるため。同じ再設定コードでの再送信は促さない。
- 「更新完了」と同じ表示にしない理由: 更新されていない場合に完了と断定することになるため。
- 新しいパスワードでのログイン（ログイン画面へ）と、申請し直し（申請画面へ）のどちらにも進めるようにする。主操作はログインとする（更新済みの可能性があり、試すだけで確かめられるため）。
- この状態に至るには有効な再設定コードを入力する必要があるため、メールアドレスの持ち主以外にアカウントの状態が伝わることはない。

### 3.6 共通の操作性

- 再設定コード欄は数字のキーボードが出る入力にする（`inputmode="numeric"`・`autocomplete="one-time-code"`）。先頭の0を落とさないよう数値型の入力欄（`type="number"`）にはしない。貼り付けを妨げない。入力の完了や貼り付けで自動送信はしない。
- パスワードマネージャーが新しいパスワードをアカウントと結び付けられるよう、申請したメールアドレスは読み取り専用のユーザー名として扱う（`autocomplete="username"`）。新しいパスワードの2つの欄は新規パスワード用の自動入力（`autocomplete="new-password"`）にする。
- 押下できる要素（2つのボタン・導線リンク・各結果表示のボタン）は最小タップ領域を下回らない。
- キーボード操作の順序は画面の視覚順（再設定コード → 新しいパスワード → 新しいパスワード（確認） → パスワードを再設定する → パスワード再設定を申請し直す → ログイン画面に戻る → フッター）に合わせる。表示のみのメールアドレスはフォーカス順に含めない。
- エラーバナーが出たときはフォーカスをバナーに移し、スクリーンリーダーにも通知する。「更新完了」「更新結果不明」に切り替わったとき、および「引き継ぎなし」を表示したときは結果の見出しにフォーカスを移す。
- 送信中であることをスクリーンリーダーにも伝える（ボタンのラベルの変化を読み上げ対象にする）。

## 4. 共通パーツ

本画面はいずれの共通パーツのオーナーでもない。各パーツはオーナー画面の既存デザインをインスタンスとして配置し、再デザインしていない。エラーバナーは共通パーツではなく、確認コード入力画面などの既存のバナーと同じ見た目で配置している。

| パーツ名 | オーナー画面 |
|---|---|
| コード入力欄 | 確認コード入力画面 |
| パスワード入力ブロック | アカウント登録画面 |
| 未認証画面レイアウト | ログイン画面 |
| グローバルフッター | ログイン画面 |
