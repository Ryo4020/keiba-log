## 1. データモデル概要

### 1.1 エンティティ一覧

| エンティティ | 役割 | DynamoDB 上の持ち方 |
|---|---|---|
| ユーザー | データ分離の単位。識別子は Cognito の `sub` | アイテムとしては持たない（分割の単位としてのみ使う） |
| 生涯収支集計 | ユーザー1人の購入額合計・払戻額合計・馬券記録件数を保持する集計データ | ユーザーごとに1アイテム |
| 馬券記録 | 一覧・編集・削除・集計の対象となる最上位の単位。記録種別でレース記録と簡易記録に分かれる | 1件につき1アイテム |
| 買い目の集合 | ボックス・ながし・フォーメーションによる一括登録で作られるまとまり。レース記録のみが持つ | 馬券記録アイテムの中にネストして保持 |
| 買い目 | 1点分の購入単位。券種・組合せ・購入額・結果状態・払戻額を持つ | 馬券記録アイテムの中にネストして保持 |

エンティティ間の関係と多重度は Miro の ER 図に示す。

ユーザーの認証情報（メールアドレス・パスワード）は Cognito User Pool が保持し、DynamoDB では扱わない。アカウントの有効化状態・パスワード再設定の申請回数などの認証に属する状態も Cognito 側の管理であり、本テーブルの対象外とする。

### 1.2 シングルテーブル設計の採否

**採用する。** 全データを1テーブルに収め、ユーザー識別子を分割の単位とする。

根拠は次の4点。

1. すべてのアクセスパターンがログイン中のユーザー1人の範囲で閉じている。ユーザーをまたぐ検索・集計・ランキングは要件に存在しない（`REQ-AUTH-004`、`REQ-SUMMARY-001` の集計対象は自分の全馬券記録）。ユーザー識別子を分割の単位にすれば、全アクセスパターンが単一パーティションへのアクセスで完結する。
2. 生涯収支集計と馬券記録を同一パーティションに置けるため、記録の登録・更新・削除と集計値の更新を1回のトランザクション書き込みで原子的に行える。`REQ-NFR-003`（記録と関連データが不整合な状態にならない）への直接的な対応になる。
3. アカウント削除（`REQ-AUTH-005`）で、そのユーザーの全データを1回のクエリで列挙して削除できる。テーブルをまたぐ削除漏れが構造的に発生しない。
4. トップレベルのアイテム種類が「馬券記録」「生涯収支集計」の2つだけで、アクセス特性も権限境界も分かれていない。テーブルを分けても得るものがなく、Lambda の IAM 権限と CDK 定義が増えるだけになる。

集計を別テーブルに分ける案も検討した。DynamoDB のトランザクションはテーブルをまたげるため技術的には成立するが、同一パーティションに置く方が整合性の担保が単純で、読み取りも1回の Query にまとめられるため採用しない。

### 1.3 買い目・買い目の集合を馬券記録アイテムにネストする

買い目と買い目の集合は独立したアイテムにせず、馬券記録アイテムの中にネストした構造として保持する。

- 買い目は常に馬券記録と一緒に読み書きされる。買い目を単位に検索・集計するアクセスパターンは存在しない（編集画面は記録1件をまとめて読み、保存も記録1件の単位で行う）。
- 別アイテムに分けると、1件のレース記録が最大で「記録1 + 買い目の集合200 + 買い目200」のアイテム数になる。トランザクション書き込みの上限（1トランザクション100アイテム）を超えるため、`REQ-TICKET-003` の保存を原子的に行えない。
- ネストすれば保存は1アイテムの更新となり、トランザクションを使わずに原子性が保証される。書き込み対象は「馬券記録アイテム」と「生涯収支集計アイテム」の2件だけになり、上限にも余裕を持って収まる。
- アイテムサイズも収まる。買い目1件が持つのは券種・組合せ（最大3つの番号）・購入額・結果状態・払戻額で、数十バイト程度。上限の200件でも数十KBにとどまり、1アイテム400KBの上限に対して十分な余裕がある。買い目の集合が持つのは券種・買い方・買い方の指定内容・1点あたりの購入額のみで、こちらも小さい。
- 「バラす」操作（買い目の集合の解体）も、同一アイテム内で買い目の所属を付け替えるだけになり、集合と買い目が食い違った中間状態が発生しない。

### 1.4 生涯収支サマリーの集計方針

**集計アイテムとして保持し、書き込み時に差分更新する。都度の全件走査は行わない。**

- 生涯集計は期間指定も絞り込みも持たず、対象は常にユーザーの全馬券記録（`REQ-SUMMARY-001` #3・#6）。都度算出するとホーム画面を開くたびにユーザーの全記録を読むことになり、読み取り量と応答時間が記録件数に比例して増える。ホーム画面は最も頻繁に開く画面であり、集計のためだけに全件を読むのは割に合わない。
- 集計アイテムが保持する値は、購入額合計 `P`・払戻額合計 `R`・馬券記録の件数の3つ。収支額 `R − P` と回収率 `R ÷ P × 100` は導出値なので保存せず、読み出し時に算出する。`P` が0のときは回収率を算出しない（`REQ-SUMMARY-001` #5）。件数は空状態の判定に使う（#8）。
- 各馬券記録アイテムに、その記録が `P`・`R` に寄与する額（集計対象額）を保持する。登録時は寄与額を加算し、削除時は減算し、更新時は「保存前の寄与額を減算して保存後の寄与額を加算」する差分更新を行う。全件の再計算は行わない。
- 寄与額の求め方は `business-rules.md` の「収支額・回収率の算出ルール」に従う。レース記録は結果状態が「返還」「結果未確定」の買い目を除いた購入額・払戻額の合計であり、結果の確定状態が「確定前」のレース記録は寄与額が0になる。簡易記録は入力された購入額・払戻額をそのまま寄与額とする。
- 加算・減算はアトミックカウンタ（`ADD`）で行い、馬券記録アイテムの書き込みと同一のトランザクション書き込みに含める。記録と集計がずれた状態が残らない（`REQ-NFR-003`）。集計アイテムが存在しない場合（そのユーザーの初回登録時）は、同じトランザクションの中で作成する。
- 読み取りは集計アイテム1件の取得で済む。登録・更新・削除の直後にホーム画面が表示されるため（`REQ-SUMMARY-001` #7）、この読み取りは強い整合性のある読み取りを使う。

トレードオフとして、集計値は記録の実体から導かれる二次データになる。差分更新（登録・更新・削除の各操作での加算・減算）を正しく実装することが整合性維持の前提になる。全件走査による再計算の仕組みは今回のスコープ外とする。

### 1.5 一覧・直近記録リストの取得方針

- 馬券記録一覧（`REQ-TICKET-005`）と直近記録リスト（`REQ-TICKET-006`）は並び順が同じ（日付の新しい順）で、取得件数と取得する属性が異なる。一覧は常に20件固定、直近記録リストは呼び出し側が指定する件数（1〜20件、デフォルト5件。ホーム画面は5件を指定して呼ぶ）を取得する。同じソート順の上で取得件数だけを変えることで両方を満たし、専用のインデックスは追加しない。
- 並び順はユーザーのパーティション内のソート順で表現する。同一日付の馬券記録が複数存在しうるため、日付だけでは順序が一意にならない。記録の識別子を併せて順序を一意にする（具体的なキー構成は `db-tables/` で定義する）。
- 一覧のページングは DynamoDB が返す `LastEvaluatedKey` をカーソルとして扱う。ページ番号を指定した任意ページへのジャンプは行わない（要件は他ページを表示する操作の提供までで、絞り込み・並び替えは禁止されている）。
- 一覧の各行に必要な情報はすべて馬券記録アイテム自身が持つため、一覧の取得で追加の読み取りは発生しない。レース記録の行に表示する「結果未確定の買い目を含むか」（`REQ-TICKET-005` #7）は、レース記録が持つ「結果の確定状態」の値をそのまま見れば判別できる。`business-rules.md` の「結果の確定状態（レース記録単位）」の通り、結果の確定状態はレース記録単位で1つに決まり、確定状態が「確定前」のときはすべての買い目が「結果未確定」、「確定後」のときは結果未確定の買い目は存在しない。買い目ごとに結果状態が異なることはないため、買い目を走査した判定処理は不要であり、記録アイテムが保持する「結果の確定状態」の属性をそのまま一覧表示に使う。
- レース記録の行に買い目の券種・組合せ・購入額を表示する要件（`REQ-TICKET-005` #6）については、一覧の取得（AP-03）で買い目の詳細まで返す。買い目は馬券記録アイテムにネストされているため（1.3）、記録アイテムを取得すれば買い目データは追加の読み取りなしにそのまま手に入る。一覧の1ページは最大20件の記録を返し、レース記録1件は買い目を最大200件持ちうるため、1回のレスポンスに含まれる買い目データの量は少なくない。UI設計上の留意点でも「全件展開は避け、件数・購入額合計などで要約した表示を検討する」とされている。表示側は買い目1件ずつを一覧に展開せず、券種ごとの件数・購入額合計といった要約に加工して見せる想定だが、その要約は取得したデータから表示側で組み立てれば足り、DynamoDB 側で要約済みの属性を別途持つ必要はない。したがって AP-03 は記録アイテムを買い目・買い目の集合を含めて取得するものとし、要約用の属性を新たに設けない。なお、Query の 1MB 上限により1ページが20件未満で返ることは許容し、継続読み取りで20件に揃えることはしない（最大20件のページングとする）。
- 直近記録リスト（AP-02）は `REQ-TICKET-006` の受け入れ基準に買い目・結果状態の表示要件がなく、UI設計上の留意点にも記載がない。AP-02 が必要とするのは馬券記録アイテムの共通属性に限られる。取得件数は呼び出し側が指定された件数（1〜20件、デフォルト5件）とし、常に先頭から指定された件数を返す（ページングは行わない）。したがって AP-02 は `ProjectionExpression` で必要な属性のみを取得し、`bets` / `betGroups` は取得しない。取得する属性の具体的な列挙は `db-tables/` で定義する。
- この射影は読み取りリクエストの指定にとどめ、キー設計・アイテム構造は AP-03 と共通とする。専用の GSI は追加しない（同じ並び順を射影だけ変えて複製することになり、書き込みコストとインデックス保守が恒久的に増える）。買い目を別アイテムに分離することもしない（1.3 の原子性の判断を崩し、AP-03 の `Limit` によるページングが成立しなくなる）。
- `ProjectionExpression` は消費 RCU を減らさない。RCU は射影前のアイテムサイズで計算されるため、読み取りコストは変わらない。目的はレスポンスサイズ・転送量・Lambda のデシリアライズコストを買い目の件数に依存しない一定量に抑えることであり、読み取りコストの削減ではない。

### 1.6 データ分離と所有者チェック

- 全アイテムの分割の単位にユーザー識別子（Cognito の `sub`）を含めるため、他ユーザーのアイテムにキーで到達できない（`REQ-NFR-001`）。
- キーに使うユーザー識別子は JWT から取得した値のみとし、リクエストボディやクエリで指定された値は使わない。
- 更新・削除は条件付き書き込みで対象アイテムの存在を確認する。他ユーザーの記録を指定した場合はキーが一致せず、存在しないものとして失敗する（`REQ-TICKET-003` #2、`REQ-TICKET-004` #6）。

## 4. 運用設計（バックアップ・TTL・ストリーム）

### バックアップ・復旧

- PITR（ポイントインタイムリカバリ）を有効にする。`REQ-NFR-004` の復旧手段はこれで満たす。
- オンデマンドバックアップは併用しない。PITR の保持期間で足りる。
- PITR からの復元は新しいテーブルへのリストアになるため、復旧は運用者による手動作業とする。ユーザー向けの復元機能は提供しない（`REQ-TICKET-004` #5、`REQ-AUTH-005` #7 が復元手段の提供を禁じている）。
- テーブルの削除保護を有効にする。

### 暗号化

- 保管データのサーバーサイド暗号化を有効にする（`designs/architecture.md` の保管データの保護に対応）。

### TTL

- **使用しない。** 論理削除を行わず、削除要求に対して即時に物理削除する。削除した記録・アカウントを復元しない要件と整合する。
- 未確認アカウントは削除されずに残る（`business-rules.md` のアカウントのルール項番5・項番11）。アカウントは Cognito User Pool が管理し本テーブルには持たないため（1.1）、未確認アカウントは DynamoDB では扱わない。

### DynamoDB Streams

- **使用しない。** 生涯収支の集計はトランザクション書き込みで同期的に更新するため、ストリームを起点とした非同期集計は不要。
- 非同期集計にすると、登録・更新の直後にホーム画面を開いたときに古い集計値が表示されうる。`REQ-SUMMARY-001` #7（反映後の値を表示する）を満たせないため採用しない。

### 読み取り整合性

| 対象 | 整合性 | 理由 |
|---|---|---|
| 収支サマリー（AP-01） | 強い整合性のある読み取り | 登録・更新・削除の直後に表示され、反映後の値である必要がある |
| 馬券記録1件（AP-04） | 強い整合性のある読み取り | 保存直後に再度編集画面を開いた場合に、保存前の内容を表示しない |
| 一覧・直近記録リスト（AP-02・AP-03） | 結果整合の読み取り | 数十ミリ秒の反映遅延が問題にならず、読み取りコストを抑えられる |

### アカウント削除の手順

- 対象ユーザーのアイテムを列挙し（AP-08）、集計アイテムを含めて一括削除する（AP-09）。
- 削除は複数リクエストに分かれるため、DynamoDB 側の削除が完了してから Cognito のユーザーを削除する。順序を逆にすると、認証情報が消えた後に残存データへ到達する手段がなくなる。
- 途中で失敗した場合は同じ処理を再実行できるようにする（同じユーザー識別子で列挙し、残っているアイテムを削除する）。
- 削除の完了後も、他端末の発行済みトークンにより、削除済みユーザーの `sub` をキーとする馬券記録が作られうる（AP-05 により集計アイテムも作り直される）。これらは本手順の削除対象に含まれずテーブルに残るが、MVP では対策を設けない。同じメールアドレスで再登録したアカウントは別の `sub` を持つため、これらのアイテムには到達しない。許容の根拠と期間は `business-rules.md` の「状態と状態遷移 > 認証状態」のルール3と `designs/architecture.md` 5.2「アカウント削除」の制約を参照する。

### 監視

- スロットリングとシステムエラーを CloudWatch のメトリクスで監視する。
- トランザクション書き込みの競合が継続的に発生する場合は、集計アイテムへの書き込み集中を疑う。同一ユーザーの同時書き込みに限られるため、通常の利用では発生しない想定。
