# 実装時の共通ルール

実装エージェント（backend-developer / frontend-developer / aws-developer / unit-test-generator）および code-reviewer が、タスクに着手する際に共通で守るルールを定義する。

## 前提: task-planner は依存関係を考慮しない

task-planner は機能（要件ID）ごとに個別起動され、**その機能を実現するために必要な実装を列挙するだけ**である。

- タスク間の依存関係・実行順序は定義されない
- 「他機能で既に実装済みかどうか」も判定されない
- タスクの概要は、常に**新規実装として**記述される

複数の機能が同じテーブル・同じAPIエンドポイント・同じ共通UIパーツ（サイドバー・グローバルフッター等）・同じ共通ロジックを必要とすることがあるため、**実装済みかどうかの確認は実装エージェント側の責務**となる。

## 実装前の確認（必須）

タスクに着手する前に、そのタスクで実装対象となっている要素が**既に実装済みでないか**を必ず確認する。

1. タスクの概要・参照仕様から、実装対象となる要素を洗い出す
2. 既存のコード・リソース定義を検索し、該当する実装が存在するかを確認する
3. 確認結果に応じて対応を分ける

| 確認結果 | 対応 |
|---|---|
| 未実装 | タスクの記述どおりに新規実装する |
| 実装済み（仕様を満たしている） | 新規実装せず、そのまま流用する。タスクの備考に流用した旨を記録する |
| 実装済み（仕様を満たすには不足がある） | **差分のみを実装する**。既存実装を作り直したり、同じものを別名で作成したりしない |

### 重複しやすい要素

以下は特に複数機能で共有されやすいため、確認を省略しない。

| 要素 | 確認先の例 |
|---|---|
| DynamoDBテーブル・GSI | 既存のCDKコード（テーブル定義） |
| APIエンドポイント・ハンドラー | 既存のルーティング定義・ハンドラー実装 |
| 共通UIパーツ（サイドバー・グローバルヘッダー／フッター等） | 既存のコンポーネント実装。オーナー画面は `ui-overview.md` の「共通パーツ一覧」を参照 |
| ドメインエンティティ・共通ロジック・バリデーション | 既存の domain 層・共通ユーティリティ |
| 認証・認可のミドルウェア | 既存のミドルウェア実装 |
| 型定義・APIクライアント | 既存の型定義・APIクライアント実装 |

## 禁止事項

- 既存実装を確認せずに新規作成すること
- 同じ役割の実装を別名で重複して作成すること
- 他機能が使用している既存実装を、自分の機能の都合で破壊的に変更すること（変更が必要な場合はユーザーに報告する）

## 完了判定

タスクの受け入れは、対応する `requirements/user-stories/<要件ID>-*.md` の受け入れ基準（EARS）をすべて満たしているかで判定する。task-planner は個別の受け入れ条件を作文しないため、この受け入れ基準が唯一の完了判定基準となる。

`tasks/foundation.md` のタスクのように対応する要件IDが存在しない場合は、`architecture.md` の該当セクションとの一致をもって完了とする。
